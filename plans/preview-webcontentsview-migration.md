# Preview: iframe → WebContents (for E2E test runs)

> Generated by swarm planning session on 2026-08-01

## Summary

The request was to replace the preview `<iframe>` with an Electron `WebContentsView`, so that E2E tests can run in the preview panel. The planning team (PM / UX / Eng) converged on a different shape of the same goal: **the E2E unlock does not come from `WebContentsView` — it comes from the preview being a _separate WebContents_, which is an addressable CDP page target.** A hidden `BrowserWindow` provides that with none of the native-compositing cost.

**Recommendation: keep the live preview on its iframe. Run tests in a hidden `BrowserWindow` and screencast it into the panel.** Ship a live Playwright step reporter first — it is independent of all of this, costs almost nothing, and delivers most of "watch your tests run" on its own. On top of that, a **synthetic cursor** driven by observed CDP input makes each step legible as an action rather than a diff (Phase 5, D9/D10).

> ⚠️ This plan **diverges from the literal request**. Four clarifying questions went unanswered (see [Unanswered Questions](#unanswered-questions)); the plan proceeds on the team's assumptions. If any answer differs — especially "do you need to preview sites that refuse iframes?" — re-open [Decision D2](#decision-log).

## Problem Statement

The stated motivation ("we become able to run the E2E tests in the preview panel") describes a mechanism, not a user problem. Interrogating it produced one dead reading and one live one.

**Dead reading — Dyad's own suite.** _Verified by the team lead:_ `frameLocator` appears **0** times in `e2e-tests/`, but `contentFrame()` appears in **11 files (~51 call sites)**. `e2e-tests/select_component.spec.ts:12-14` clicks a heading _inside_ the preview; `e2e-tests/helpers/page-objects/components/PreviewPanel.ts:323-329` ARIA-snapshots the preview `body`. Dyad's own Playwright suite already reaches into preview content through the iframe. Nothing is blocked.

**Live reading — the user's app tests.** Here the iframe genuinely does block something, and the reason is precise. Playwright's Electron driver turns every CDP target of `type === "page"` into a `Page` (`playwright-core/lib/server/chromium/crBrowser.js:156`). An OOPIF is **not** a target — it is a `Frame` of Dyad's renderer page. So today a generated spec could only ever be `dyadRendererPage.frameLocator(...)`, where `page.goto('/')`, `page.reload()`, `expect(page).toHaveURL()`, and `context.clearCookies()` either fail or operate on **Dyad's own renderer**. Since these specs are written by an AI and must survive leaving Dyad, a bespoke frame-only dialect is a **Productionizable** (principle 2) violation.

The user-facing problem, stated properly:

> A Dyad user asks for a test. Today that triggers a package-manager install, sometimes a ~100MB browser download, and then a foreign Chromium window that steals focus, renders their app at the wrong size, and disappears — while the panel showing their app sits inert two inches away. Time-to-first-green-test is minutes, and the moment a test fails the user is looking at a JSON-derived list, not the failure.

### What the migration would cost

`PreviewIframe.tsx` is 1632 lines, backed by a 6-module state machine (`src/preview_iframe/`), a second state machine for screenshots (`src/screenshot/`), and epoch-keyed capability leases (`src/window_infrastructure/`). Every Dyad↔app channel is `postMessage`.

The load-bearing constraint: **a `WebContentsView` is a native child view composited _above_ the renderer's DOM.** Nothing in Dyad's React tree can paint over it — not the error banner, not the loading screen, not the visual-editing toolbar, not a tooltip. "No regressions in the UX" is therefore not a constraint that can be satisfied by construction on the live preview; it is a long polish tail on the surface principle 6 calls _"the core of what makes Dyad feel alive."_

## Scope

### In Scope (MVP)

- **Live Playwright step reporter** — stream `onTestBegin`/`onStepBegin`/`onStepEnd`/`onTestEnd` into the Tests panel. Independent of everything else.
- **Hidden `BrowserWindow` preview WebContents** for test runs, driven over CDP.
- **Filtered CDP endpoint** with a per-run token, exposed to the user's Playwright process as `DYAD_CDP_ENDPOINT`.
- **Screencast into the preview panel** (`Page.startScreencast` → `<canvas>`/`<img>` in existing DOM).
- **Test-drive mode UI**: run bar, step rail, "Tests are driving this preview" chip, pause-on-failure with `[Fix with AI]`.
- **Synthetic cursor** — a drawn pointer that travels between the elements each step acts on, driven by real `Input.dispatchMouseEvent` coordinates observed at the proxy (see D9).
- **Three-way run toggle**: Headless · **Watch in Dyad** (new default) · External window (retained — principle 5).
- **`iframeEpoch` → `previewSurfaceId`** prerequisite refactor.
- **Transport-interface refactor** of `previewIframeRefAtom` / `VisualEditingToolbar` / `useShortcut` — done against the iframe.

### Out of Scope (Follow-up)

- **Migrating the live preview to `WebContentsView`** — deferred indefinitely; needs a driver of its own (see D2).
- Removing `@playwright/test` from the user's app — **explicitly rejected**, violates principles 2 and 5.
- Clicking into a running test (take-control mid-run). "Take control" = stop the run, return to live preview.
- Per-app `session.fromPartition`, native nav history, CDP console/network capture, DevTools-on-preview — all real wins, but they belong to the full migration.

## User Stories

- As a **Dyad user running generated tests**, I want to watch the run in the panel I'm already looking at, so I don't lose context to a window that steals focus.
- As a **Dyad user whose test just failed**, I want the run to freeze on the failing frame with the assertion and a Fix-with-AI button, so I can act instead of decoding a JSON report.
- As a **Dyad user on macOS or Linux without Chrome**, I want tests to run without a ~100MB browser download.
- As a **user shipping to production**, I want my `e2e-tests/` specs to run under plain `npx playwright test` in my own CI, so Dyad is not a dependency of my test suite.
- As a **Dyad contributor**, I want the ~150-spec suite to stay green through this work.

## UX Design

### User Flow

1. User opens the **Tests** tab, presses **Run** with the toggle on **Watch in Dyad**.
2. The Preview tab activates and enters **Test-drive mode**. The live iframe stays mounted underneath — **it is never unloaded**.
3. The browser toolbar row is replaced in place by a run bar: `▸ should sign in · step 4/11 · [1x ▾] [Pause] [Stop]`. The address bar goes read-only and mirrors where the test navigated.
4. A **step rail** docks to one side, fed by real reporter events. The current step is highlighted; past steps are hoverable to scrub their captured frame.
5. The screencast plays in the preview rect. A teal chip reads **"Tests are driving this preview · Take control"**.
6. **On failure, the run pauses by default.** The frame freezes; a red bar docks below with `should sign in failed at step 4 · expect(locator).toBeVisible()` and `[Fix with AI]` (wired to the existing `askAiToFix` — one path, no fork), `[Show screenshot]`, `[Open trace]`.
7. Run ends → in-panel `3 passed · 1 failed` summary → the panel returns to the live preview, **exactly where the user left it** — logged in, scrolled, mid-form.

### Key States

- **Default**: unchanged live preview on the iframe. Zero delta.
- **Loading**: existing `PreviewLoadingScreen` — unchanged, because nothing native is composited.
- **Empty**: "No tests yet — Generate one" → existing `generateTest`.
- **Running**: screencast + run bar + step rail; guest input ignored.
- **Paused / failed**: frozen frame (stop updating the canvas — free), red failure bar.
- **Error**: existing `ErrorBanner` — unchanged.

### Interaction Details

- **Element highlighting** (seeing the button light up before Playwright clicks it) — CDP `Overlay.highlightNode` renders inside the page compositor, so it survives screencast and would survive a native view. Free.
- **Input blocking** — CDP `Input.setIgnoreInputEvents` ignores real user input while still accepting Playwright's synthesized events. Exactly the required semantics.
- **Step scrubbing** — one `capturePage()` per step. Cheap.
- **Pause-on-failure** — stop updating the canvas. No freeze machinery, no capture race.
- **Fidelity** — JPEG @ ~15fps is fine while watching (slow-mo already runs below 60fps); switch to `format: "png"`, device-scale-matched, while paused.

#### The synthetic cursor

**Playwright never moves the OS cursor.** It synthesizes input straight into the renderer via CDP `Input.dispatchMouseEvent`; the user's real pointer never moves, and even a headed run shows buttons depressing with nothing visibly travelling. It also teleports — `locator.click()` sends one `mouseMoved` to the element centre, then press, then release, with no intermediate positions.

So the cursor the user sees is **entirely drawn by Dyad**. That is a feature: there is no real pointer to stay faithful to, so path, easing, and speed are chosen purely for legibility.

- **Coordinates come free.** The proxy already sits in the CDP path and sees every `Input.dispatchMouseEvent` go by with exact viewport CSS pixels. **Do not** parse selectors out of reporter step titles and re-resolve them — that is string-matching against a format Playwright does not guarantee, and it can point at a different element than the one actually hit.
- **Hold the click so the motion means something.** Naively animating a 300ms glide loses the race: `mousePressed` follows `mouseMoved` immediately, so the button clicks itself before the cursor arrives. Because the proxy is a man-in-the-middle, it can **delay forwarding the `mousePressed` frame** until the animation lands — Playwright is `await`ing that command anyway. Cursor arrives, *then* the click. This is only possible because we own the proxy, and it is the strongest argument for the proxy design.
- **The target's `:hover` is real.** Playwright genuinely moves to the element centre before pressing, so the button lights up on its own in the screencast exactly as the drawn cursor arrives. Free reinforcement.
- **Render**: arrow with eased motion (travel time scaled to distance, brief settle before the press), faint trail from the previous position, click ripple sized to `clickCount`, and a small label riding the cursor with the step title (`click "Sign in"`) tying the motion to the step rail.
- **Non-mouse steps need a second path.** `fill()` focuses and then uses `Input.insertText` — no mouse event, no coordinates. Fall back to reading `document.activeElement`'s box over CDP when a text step begins; workable, less clean than the mouse path.

### Draw it inside the guest

Two places the cursor could live. Over the screencast canvas in Dyad's DOM is easier — `Page.screencastFrame` metadata (`pageScaleFactor`, `deviceWidth`, `scrollOffsetX/Y`) gives the mapping per frame — but it **only works in screencast mode**. Inside the guest page (`pointer-events: none`, closed shadow root) it renders in the page's own compositor and therefore survives **both** screencast and a native `WebContentsView`.

Given U2 is unresolved, **build it inside the guest.** Dyad already ships `worker/dyad-component-selector-client.js` (23KB) and `worker/dyad-visual-editor-client.js` (9.3KB) drawing exactly this kind of overlay, so the pattern and the injection plumbing exist.

### Accessibility

- `aria-live="polite"` announces each step transition, mirroring the existing counter in `TestsPanel.tsx`.
- The step rail is a real list with keyboard traversal; the run bar's controls are real buttons in the normal tab order.
- Because the screencast is an ordinary DOM element, **focus, Tab traversal, tooltips, and `⌘⇧C` all keep working** — none of the focus-root problems a native view introduces apply.
- Failure text is selectable and copyable (monospace in a contained box, matching existing error treatment).

## Technical Design

### Architecture

```
┌─ Dyad renderer ────────────────────────────┐     ┌─ hidden BrowserWindow ─┐
│  PreviewPanel                              │     │  preview WebContents   │
│    ├─ <iframe>          (live, unchanged)  │     │  = CDP page target     │
│    └─ <canvas>          (screencast)  ◄────┼─────┤  Page.startScreencast  │
│  Test-drive chrome (run bar, rail, bars)   │     └───────────┬────────────┘
└────────────────────────────────────────────┘                 │
                                                    ┌──────────▼──────────┐
   user's `npx playwright test`  ──ws://token──►    │ main: filtered CDP  │
   (DYAD_CDP_ENDPOINT)                              │ proxy + reporter    │
                                                    └─────────────────────┘
```

**Verified**: `playwright-core/.../chromium.js:335-337` — `urlToWSEndpoint()` returns the URL unchanged when it starts with `ws`, so Playwright **never fetches `/json/version`** for a `ws://` endpoint. Dyad can be the CDP server.

**But two constraints survive**, and they shape the design:

1. The connection is **browser-level, not page-level**. `CRBrowser.connect` (`crBrowser.js:66-80`) immediately sends `Browser.getVersion`, then subscribes to `Target.attachedToTarget`/`detachedFromTarget` and `Browser.downloadWillBegin/Progress`. `webContents.debugger` is page-scoped — no `Browser.*`, no target discovery. Building a relay on `webContents.debugger` alone means **synthesizing the entire Browser + Target domain**: not a shim, a CDP server implementation, permanently fragile against every Playwright minor. **Do not do this.**
2. `WebSocketTransport` is **`ws` over TCP only** (`transport.js:99`) — no Unix socket, no named pipe. `--remote-debugging-pipe` is unreachable for a shipped app (the parent must own fds 3/4). Something listens on loopback regardless.

So: launch with `--remote-debugging-port=0`, read the ephemeral port, and have main host a **~200-line filtering WS proxy** on its own loopback port with a per-run random token in the path. It forwards frames, drops `Target.attachedToTarget` for non-preview targets, and rejects `Target.attachToTarget`/`Target.createTarget` for others. The user's test process only ever learns `ws://127.0.0.1:<proxyPort>/<token>`.

The proxy earns its keep twice: besides filtering, it is the only component that sees the raw input stream, which is what makes the synthetic cursor exact rather than inferred. It has two jobs there — **observe** `Input.dispatchMouseEvent` coordinates, and **hold** the `mousePressed` frame while the cursor animates. The hold must be bounded, opt-in to Watch-in-Dyad, and never applied on the headless path.

**Residual risk, stated plainly for security review**: the real Chromium debugging port stays open on loopback for the process lifetime, and `/json/*` on it discloses the renderer's WS GUID to any local process. The proxy protects the _user's tests_ from seeing Dyad's renderer; it does **not** protect Dyad from a hostile local process, and the switch is launch-time-only. Mitigations: (a) accept it — Chrome ships this posture; or (b) **spawn a dedicated hidden helper Electron process** owning the debugging port and hosting only the preview WebContents, closing the RCE surface entirely. **(b) is the team's recommendation; this decision is unanswered — see U3.**

### Data Model Changes

None persisted. In-memory only:

- `previewSurfaceId` replaces `iframeEpoch` as capability-lease identity. Epoch does **two** jobs today — React remount identity **and** a monotonic generation token so a stale window can't claim a lease for a dead surface. Only the first disappears. The replacement is the preview `webContents.id`: stable for the view's lifetime, monotonic across the process, and **strictly better** than epoch because it's minted in main (the authority) rather than reported by a renderer over IPC.
- Per-run CDP token (ephemeral, never persisted).
- Step-rail state in the existing `testRuntimeAtoms`.

### API Changes

- **`DYAD_CDP_ENDPOINT`** (env var, Dyad → user's Playwright process). The generated config falls back to a normal launch when absent:
  ```ts
  const cdp = process.env.DYAD_CDP_ENDPOINT;
  export default defineConfig({
    use: { ...(cdp ? { connectOptions: { wsEndpoint: cdp } } : {}) },
  });
  ```
  `connectOptions`/`connectOverCDP` has been stable since Playwright 1.12, so this survives version skew. **Acceptance criterion: generated specs must run under bare `npx playwright test` with Dyad absent.**
- **`@@DYAD_STEP {json}`** stdout protocol (reporter → main → renderer).
- **`PreviewIframeTarget`** (`src/preview_iframe/commands.ts:8-10`) is already a one-method interface, so a `MessagePort` satisfies it unchanged.

## Risks & Mitigations

| Risk | Likelihood | Impact | Mitigation |
| --- | --- | --- | --- |
| Loopback CDP port reachable by any local process → RCE via Dyad's renderer preload | M | **H** | Dedicated hidden helper process (preferred) or filtering proxy + token; **route to security review before code** (U3) |
| Debugger contention — `webContents.debugger.attach()` fails if another client is attached | H | M | One owner. Do **not** ship CDP console/network capture and the test unlock against the same target without a multiplexer |
| User-pinned `@playwright/test` version skew against Electron 40's Chromium | M | M | `connectOptions` stable since 1.12; pin a tested floor; spike with a user-pinned version (Phase 3) |
| Migration churn lands in an already-red suite | H | M | Deflake `visual_editing` + `cloud_sandbox` **first** (Phase 2) |
| Screencast fidelity/latency disappoints | L | L | User is watching, not interacting; PNG device-scale-matched while paused |
| Scope creeps back toward full `WebContentsView` migration | M | H | D2 records the bar: it needs a driver of its own |
| `Browser.*` domain gaps if anyone revisits a `webContents.debugger` relay | L | H | Explicitly rejected in this plan; re-read `crBrowser.js:66-80` before reconsidering |
| **Cursor hold inflates run time into test timeouts** — ~250ms × 50 actions ≈ 12s against a 30s default | M | **H** | Hard-cap the hold; headless untouched; regression gate asserts watch mode never changes a verdict; surface "this run timed out only in watch mode" in the UI rather than reporting a failure |
| **Guest-drawn cursor appears in `toHaveScreenshot()`** | M | H | Tear down around `Page.captureScreenshot`; prefer `Overlay.*` substrate if the spike confirms it is excluded from captures |
| Cursor path implies causality that did not happen (glides over a nav item that never received a hover) | M | L | Accepted — D10. Keep paths short and direct; never interpolate into the real input stream |

## Unanswered Questions

Four questions were put to the human and went unanswered. The plan proceeds on the team's assumptions; each of these can change it.

- **U1 — Approach.** _Assumed: hidden `BrowserWindow` + screencast._ If the answer is "full migration as asked," the UX regression inventory below becomes the plan.
- **U2 — Other drivers.** _Assumed: E2E only._ **The one answer that flips the recommendation is "we need to preview sites that refuse iframes"** — OAuth popups, Stripe/Auth0 redirects, third-party embeds sending `X-Frame-Options` / `frame-ancestors` / COOP. An iframe cannot solve that at any price, and it would justify the full migration on its own.
- **U3 — CDP security posture.** _Assumed: dedicated helper process._ Blocks Phase 3's design; the residual-risk paragraph above is written for whoever owns this call.
- **U4 — Visual-editing toolbar.** _Assumed: separate phase (Phase 6), not blocking._

### Deferred: the full-migration regression inventory

UX priced 18 regressions against a full `WebContentsView` migration. Kept here so the work is costed if U2 reopens it.

**Blocks ship (8)** — error banner → layout sibling; `PreviewLoadingScreen` → `capturePage()`-and-blur (today it blurs the _last painted app frame_; a native view leaves an opaque card over a hole); 12+ tooltips and 3 downward menus occluded (they portal to `document.body`); panel-resize desync, including `chat.tsx:150,199` `transition-all duration-100` on panel width — **a CSS transition a native view physically cannot follow**; focus root breaks Tab traversal and the `⌘⇧C` relay; right-click menu **lost entirely** (`main.ts:981` installs it on the _window's_ webContents); navigation guards after `sandbox=` disappears (`PreviewIframe.tsx:1544`); 51 `contentFrame()` sites.

**Before default-on (8)** — docked visual-editing toolbar; window move / fullscreen / DPI; ancestor scroll (`PreviewPanel.tsx:175` is `flex-1 overflow-y-auto`, so a native view stays pinned while chrome scrolls under it); border radius; dark-mode flash (a fresh WebContents paints white); device-mode transition; multi-window view keying; Annotator hide.

**Later (2)** — tab-switch state preservation (a _change_, not a regression — today it reloads — and it needs a mute policy for audio/timers); zoom decoupling.

**If it is ever built, one architectural invariant makes it tractable**: _no Dyad pixel is ever drawn over the view; overlays shrink its bounds instead._ Run bar replaces the toolbar row; step rail shrinks width; failure bar shrinks height; the one element that must float over content — the "tests are driving this" chip — is drawn **inside the guest** by the already-injected client script.

## Decision Log

- **D1 — The unlock is "separate WebContents," not "`WebContentsView`."** `crBrowser.js:156` promotes CDP `type: "page"` targets to Playwright `Page`s; an OOPIF is only a `Frame`. Any separate WebContents qualifies, and a hidden `BrowserWindow` has zero geometry cost.
- **D2 — Do not migrate the live preview.** All three roles independently concluded the E2E reason does not justify it. Reopen only with a driver of its own (U2).
- **D3 — Screencast beats a pinned `WebContentsView` for test runs.** Eng's Option B (pin a real view to the preview rect during a run) costs **two app reloads per run** — the second dumps the user back into a cold app, losing the logged-in/scrolled/form-filled state they had before pressing Run. Screencast keeps the iframe mounted throughout: zero reloads, every overlay composites normally, pause-on-failure is free.
- **D4 — `@playwright/test` stays installed in the user's app.** Dropping it would replace the user's toolchain (principles 2 and 5). `playwrightInstallCommand` is untouched. **The pitch is "no browser _download_," never "no install."**
- **D5 — The visual-editing toolbar fix is worth doing regardless.** It has three live bugs today: `VisualEditingToolbar.tsx:358-359` positions at `coordinates.top + height + 4` / `coordinates.left` inside the container at `PreviewIframe.tsx:1495`, but in tablet/mobile the wrapper is `flex justify-center` around a fixed 375/768px child (`:1517-1520`) — so **the toolbar is offset from its element by the full gutter in two of three device modes**; near the viewport bottom it renders below the fold and is clipped by `overflow-hidden`; near the right edge its popover row overflows.
- **D6 — The Chromium-download argument is weaker than first claimed.** Re-reading `playwright_bootstrap.ts:149-204`: Windows checks Chrome then **Edge** (preinstalled on Win10+) → download essentially always avoided. macOS → only Chrome-less Macs. Linux (`:196-203`) deliberately excludes distro `chromium` → high download rate, but a small share of users. **A minority hit it.** The better argument is determinism: `channel: "chrome"` drives the user's auto-updating browser (the test environment can change overnight), corporate `RemoteDebuggingAllowed=false` breaks Playwright outright, and headed runs pop the user's real browser. A pinned Electron-Chromium is more deterministic than either.
- **D7 — `plans/better-e2e.md` is a prerequisite, not a competitor.** Different budget (internal DX vs. user-facing), but `visual_editing.spec.ts` is both its top flake source and a `contentFrame()` consumer.
- **D8 — Reject a `webContents.debugger`-only CDP relay.** It would require synthesizing the entire Browser + Target domain (`crBrowser.js:66-80`), and every Playwright minor can add a browser-domain call you didn't implement.
- **D9 — Drive the cursor from observed CDP input, not from parsed step titles.** The proxy already sees every `Input.dispatchMouseEvent` with exact viewport coordinates. Re-resolving a selector scraped from a reporter title is string-matching against an unguaranteed format and can point at a different element than the one the test actually hit. Corollary: the proxy holds `mousePressed` for the animation duration so the cursor arrives *before* the click — the ordering is the entire point of the feature.
- **D10 — The cursor is a presentation layer and must never touch the input stream.** The animated path is a dramatization: the page received one jump, not twenty interpolated moves. Expanding one `mouseMoved` into many at the proxy would make the page fire hover handlers along the path and make watch-mode runs behave differently from headless ones. **Accept that the path is narrative and keep the input stream byte-identical.** The one genuinely real cue — the target's own `:hover` firing as Playwright moves to the element centre — is free and does the heavy lifting.
