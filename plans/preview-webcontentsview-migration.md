# Preview: migrate from `<iframe>` to Electron `WebContentsView`

> Generated by swarm planning session on 2026-08-03 (PM / UX / Engineering)

## Summary

Dyad's live preview is an `<iframe>` fed by a local injecting proxy, with all
renderer↔preview communication over `window.postMessage`. This plan replaces
that iframe with an Electron `WebContentsView` — a main-process-owned native
view composited above the DOM — so the preview becomes a real top-level browser
context.

The work is staged so that **everything with user-visible value or migration
risk is separated from the renderer swap itself**. Phase 1 lands a transport
bridge and a set of overlay redesigns _on the existing iframe_, with zero
user-visible regression and no feature flag. Only after two cheap phase-0
measurements do we commit to native rendering.

## Problem statement

The idea arrived as a solution ("replace the iframe"), not a problem. Restated
as user problems for Dyad's actual user — the non-technical builder in their
first hour, who reads unexplained states as "it's broken":

**The preview lies in four ways.**

1. **The device modes are fake.** `PreviewIframe.tsx:1554` is literally
   `style={{ width: "375px" }}`. `100vh`, `dvh`, DPR, touch, `@media (hover:none)`
   and the UA string all still say desktop. Users building mobile-first ship
   broken mobile layouts and cannot tell why. This is a _Productionizable_
   (principle #2) failure, not cosmetics. **This is the primary problem.**
2. **Back/forward are heuristics.** Navigation state is reconstructed from
   `postMessage` hooks in `src/preview_iframe/commands.ts` rather than real
   browser history.
3. **Screenshots are lossy.** The Annotator rasterizes via injected
   `html-to-image`, which misses canvas/WebGL and cross-origin images.
4. **Preview hangs look like Dyad breaking.** The iframe shares the renderer
   process, so an AI-written infinite loop freezes Dyad's own UI.

**Plus a narrower fifth: top-level redirect flows are dead ends.** OAuth
redirects (Google/Clerk/Auth0 hosted pages), Stripe Checkout redirects and
payment returns set `X-Frame-Options: DENY` and are refused inside a frame.
These are exactly the flows that matter most for taking an app to production.

> **Scope correction made during planning.** The initial framing claimed all
> third-party embeds are blocked. That is wrong: a widget the user's app embeds
> as a _nested_ iframe (Stripe Elements, a Maps embed) is refused at any
> nesting depth, so a top-level view does not rescue it. Nesting depth does
> shift the `frame-ancestors` ancestor chain from `[localhost:PORT, file://]`
> to `[localhost:PORT]`, which newly admits third parties that allowlist
> `localhost` explicitly — real, but narrow. **The dominant win is top-level
> navigation, not embeds.**

### What is explicitly _not_ a justification

Native devtools for the preview, per-app session partitions, and retiring the
injecting proxy are engineering hygiene. They may ride along in later phases,
but they do not justify the program and were cut from the value case.

## Decision gate

Phases 2+ are funded only if **both** phase-0 results come back positive.

| Gate                      | Pass condition                                                                                                                            |
| ------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------- |
| **G1 — E2E reachability** | Playwright (or a CDP attach) can drive a `WebContentsView` with _both_ real input synthesis and `toMatchAriaSnapshot`. Partial is a FAIL. |
| **G2 — Frequency**        | Composite signal ≥15% of active apps, or framing refusals alone ≥8%. See below.                                                           |

### G2 in detail

**Unit: share of active apps hitting the condition at least once in a 14-day
window** — not rate-per-session. These are _blocking_ failures: the first
framing refusal in an OAuth flow stops the user cold; the fiftieth does not hurt
more. Per-session rates also flatter us, because blocked users either retry
repeatedly (inflating the denominator) or churn (leaving it).

**Composite = union, deduplicated per app, of three cheaply-measurable signals:**

1. **Framing refusals** — the console-message counter (Spike 2), plus
   `did-fail-load` / `ERR_BLOCKED_BY_RESPONSE` on top-level preview navigation.
2. **Preview-attributed renderer hangs** — measurable today with no bridge:
   main-process `unresponsive` on the product window, attributed when the
   preview was mounted.
3. **Device-emulation exposure** — the #1 problem is instrumentable in phase 0
   with zero runtime cost: a static scan of the user's repo for
   mobile-conditional code (`100vh`/`dvh`, `@media (hover:none)` /
   `pointer:coarse`, `matchMedia`, `maxTouchPoints`, touch handlers)
   **intersected with** non-desktop device-mode toggle usage. That intersection
   is precisely the population we are actively lying to.

**Excluded from the gate:** lossy screenshots (Pro-only, small, and
`capturePage()` is a late freebie) and back/forward heuristics. Instrument the
"back press followed within 5s by a reload or address edit" signal, but treat
both as Amber tiebreakers only.

| Outcome   | Condition                                                        | Action                                 |
| --------- | ---------------------------------------------------------------- | -------------------------------------- |
| **Green** | composite ≥15% of active apps, **or** framing refusals alone ≥8% | Fund phases 2+                         |
| **Amber** | composite 5-15%                                                  | Fund phase 2 only; re-gate at its exit |
| **Red**   | composite <5% **and** framing refusals <2%                       | Stop at the bridge                     |

Why those lines: the cost side is roughly three quarters plus overlay changes
that touch **100%** of preview users. Below 5% of apps, that is a multi-quarter
program against a long tail — guaranteed cost, uncertain benefit. Above 15% it
is mainline work.

**Three independent no's. Any one stops the program at Phase 1:**

1. **Red** on G2 above.
2. **G1 fails** — already decided; no frequency number rescues it.
3. **The overlay pre-migration proves user-hostile on the iframe.** It is
   strictly easier there than on a view, so if it does not land well on the
   easy path, it will not land on the hard one.

**If G1 fails, the program stops at Phase 1 and the iframe stays.** This was an
explicit decision: no permanent dual-renderer fork, and no `E2E_TEST_BUILD`-gated
eval bridge. Phase 1 is designed to stand alone as a net improvement so that
outcome still leaves the codebase better.

- `before-input-event` shortcut forwarding and a focus enter/exit contract.

### Out of scope

- **Visual editing on the native path.** Visual editing stays on the iframe.
  (Decision D2.)
- **The docked inspector rail.** Deferred as a standalone product decision on

- **Warm/retained hidden views.** Destroy-on-tab-switch, as today. (Decision D5.)

- **A cloud-mode-only rollout.** Withdrawn; no technical rationale survives.

## Key findings that shaped this plan

These are load-bearing and were each verified against the code during planning.

1. **The injected clients are hardwired to iframe semantics.**
   `worker/dyad-shim.js:3-4` is literally
   `const isInsideIframe = window.parent !== window; if (!isInsideIframe) return;`.
   In a top-level view, `window.parent.postMessage(...)` posts _to itself_, so
   all 28 send sites across five clients would silently loop back. Four inbound
   guards (`shim:86`, `selector:579`, `visual-editor:308`, `screenshot:194`)
   compare `event.source !== window.parent` and fail closed.

2. **The proxy cannot be retired, and runs locally in _both_ runtime modes.**
   `ensureProxyForRunningApp` (`app_runtime_service.ts:383-495`) starts a local
   proxy on `getAppProxyPort(appId)` in cloud mode too — cloud only adds
   `fixedHeaders: { Authorization: Bearer … }` (`:474-479`), and
   `selectRemoteAppUrl` (`app_run/selectors.ts:31-41`) returns that local URL in
   both. The browser-facing origin is always `http://localhost:<proxyPort>`.
   A preload cannot replace injection either: with `contextIsolation: true` the
   preload runs in the isolated world, while these clients patch
   `history.pushState`, `console` and `fetch`/XHR in the main world.

3. **The proxy does not strip framing headers.** `proxy_server.js:435-443`
   copies `{...upRes.headers}` and deletes only `content-encoding` and `etag`.
   No `x-frame-options` / `frame-ancestors` / `content-security-policy` handling
   exists anywhere in `worker/`. It is also moot for third parties, which the
   browser fetches directly from their own origins.

4. **The drag-jank premise does not hold.** `src/pages/chat.tsx:150` and `:199`
   are `cn(!isResizing && "transition-all duration-100 ease-in-out")` — the
   transition is **already disabled during an active resize**. There is no CSS
   animation to desync from during the split drag; rAF-coalesced bounds lag ~1
   frame, which reads as normal. The 100ms transition runs only on programmatic
   collapse/expand, a discrete event where hide + placeholder is adequate.

5. **Renderer zoom breaks bounds math.** `layout.tsx:167` calls
   `webFrame.setZoomFactor(zoomLevel / 100)` on the host renderer.
   `getBoundingClientRect()` returns CSS px in the zoomed space; `setBounds`
   takes DIPs. At 150% zoom the view lands ~50% off — **broken on arrival for
   every non-100% user.** This is a correctness bug, not a11y polish.

6. **The blank-preview frequency is measurable today for ~20 lines.**
   `PreviewIframe.tsx:578-609` already funnels every preview console message
   through `ipc.misc.addLog`. Chrome's framing refusals ("Refused to display
   … 'X-Frame-Options'", "… violates … frame-ancestors") surface there verbatim.

7. **The visual-editing toolbar has no collision detection.**
   `VisualEditingToolbar.tsx:358-359` is `toolbarTop = coordinates.top +
coordinates.height + 4; toolbarLeft = coordinates.left` — no flip, no shift.
   It clips below the fold near the viewport bottom and slides out from under
   the cursor on scroll. (Recorded as pre-existing debt; not fixed here.)

## User stories

- As a builder making a mobile app, I want the mobile toggle to show a real
  phone viewport — height, pixel density and touch — so what I ship matches
  what I saw.
- As a builder wiring up Google sign-in, I want the redirect to actually load
  in the preview so I can test the flow without leaving Dyad.
- As a builder whose AI wrote an infinite loop, I want Dyad to stay responsive
  so I can ask it to fix the code.
- As an existing user, I want click-to-select, visual editing and the console to
  work exactly as before after updating.
- As a keyboard user, I want to enter and leave the preview without a mouse, and
  I want Dyad's shortcuts to keep working when the preview has focus.

## UX design

### The flag is a device-testing surface, not a preview replacement

Named **"Device preview (beta)"** — not "new preview engine". Description:

> Runs your app in a real browser view so mobile sizes, touch and `100vh`
> behave like a real device. Select-component and visual editing aren't
> available yet.

Stating the trade-off up front converts a missing feature into a known
limitation rather than a wall.

### Visual editing in native mode

Both entry points (`preview-pick-element-button` and the annotator button) stay
**visible and enabled**. Clicking either opens a popover anchored to the button:

> **Not available in device preview**
> Select-component and visual editing need the classic preview. Device preview
> runs your app in a real browser view they can't reach into yet.
> **[Switch this app to classic preview]** · [Cancel]
> _Your app will reload._

The switch is explicit, per-app and user-initiated. A silently disabled button
is a dead end (PRODUCT.md #1); an automatic renderer swap would silently destroy
in-app state mid-task.

### Overlay policy — three tiers

Bounds **are** the page viewport, so "shrink the view to vacate a rect" is
forbidden: it reflows the user's app and fires their media queries, corrupting
the device fidelity the migration exists to buy.

| Tier                    | Mechanism                                                  | Applies to                                                                                   |
| ----------------------- | ---------------------------------------------------------- | -------------------------------------------------------------------------------------------- |
| **1 — Inset**           | Persistent chrome is a flow sibling; the view rect shrinks | ErrorBanner; the `PreviewPanel.tsx:175` scroll offset                                        |
| **2 — Hide**            | `setVisible(false)` + theme-colored placeholder            | PreviewLoadingScreen, Annotator, app-wide modals, programmatic collapse, non-active tab      |
| **3 — One-shot freeze** | Single `capturePage()` on `pointerdown`, no cache          | The three dropdowns (`:1228`, `:1343`, `:1440`) — and test whether Tier 2 suffices even here |
| **0 — Geometry**        | No view interaction at all                                 | Tooltips (`side="top"`), toasts (repositioned)                                               |

A rolling frame cache was proposed and **rejected**: `capturePage()` resolves in
the main process and PNG encoding is synchronous main-thread work. At a 900×700
panel @2× DPR that is an 1800×1400 readback plus encode. Main is also the
chat-stream producer, so a periodic capture would trade preview jank for chat
stutter. Under HMR the cached frame is stale within ~1s — worst exactly when the
user is iterating. Gesture-timed capture on `pointerdown` gets 60-150ms of human
reaction time for free and needs no cache.

### Overlay pre-migration (ships on the iframe, Phase 1)

1. **Inset ErrorBanner** (`PreviewIframe.tsx:137`). Drop
   `absolute top-2 left-2 right-2 z-10`. The container at `:1495` becomes
   `flex flex-col`; the banner becomes a `shrink-0` flow sibling above the
   preview surface, which becomes `flex-1 min-h-0 relative`. Cap the expanded
   state at `max-h-[40%] overflow-y-auto` so a long stack trace cannot eat the
   preview. Keep `data-testid="preview-error-banner"`.
2. **Tooltips → `side="top"`** on every `TooltipContent` in the toolbar
   (`:1088-1491`): picker, annotator, cloud badge, back, forward, device mode,
   refresh, open-in-browser, restart. Set `collisionBoundary` to the preview
   panel so they never re-flip downward.
3. **Sonner → `position="bottom-left"`** (`layout.tsx:229`). When
   `isChatPanelHidden` (chat at 1%, `chat.tsx:136`) accept partial occlusion.
   Never shrink the view to make room.
4. **Toast-as-only-signal audit.** `:786` image-load failure → inline in
   `ImageSwapPopover`'s existing error slot (`ImageSwapPopover.tsx:168`), where
   attention already is; drop the toast. `:376` clear-cache failure → the inset
   ErrorBanner. Keep `showSuccess("Preview data cleared")` as a toast — a
   skippable confirmation.
5. **`suppress()` arbiter.** Reason-keyed
   (`modal | menu | drag | tab | annotator | not-preview-tab`), highest priority
   wins, **refcounted** so closing one of two dialogs does not unsuppress.
   Contract: suppressed → no input reaches the preview; unsuppressed → live
   within one frame; suppression never outlives the surface that caused it. In
   iframe mode it drives `inert` + `aria-hidden`, which **fixes a live bug**:
   today the iframe stays Tab-reachable behind an open modal.

### Device emulation first encounter (Phase 2)

Inline callout inside the preview panel, directly below the toolbar, in the same
flow slot the inset banner uses. Not a toast (dismissed unread), not a modal
(blocks the thing they are trying to look at). Shown once per install, on first
mobile/tablet selection after the update.

> **Mobile preview is real now**
> Dyad emulates a 375 × 812 phone — screen height, pixel density and touch.
> `100vh`, `dvh` and media queries behave like they do on a device, so your app
> may look different here than before.
> **[Got it]** · **[Fix mobile layout with AI]** · [Use width only]

"Fix mobile layout with AI" reuses the `streamMessage` pattern at `:1500`.
"Width only (legacy)" lives in the device-mode popover (`:1252`) as a checkbox
beneath the `ToggleGroup`, helper text _"Resize the frame without emulating the
device."_ — per-app, persisted next to `previewDeviceMode`. Not global settings.

Framing matters: real emulation does not break apps, it **reveals apps that were
already broken on real phones**. Shipping it with an AI fix affordance turns the
day-one surprise into Dyad catching a real bug.

### Accessibility acceptance criteria

**Blocking the default flip:**

1. **`before-input-event` forwarding**
   - Focus inside preview + Cmd/Ctrl+R → Dyad reloads the preview (not the
     page's own reload).
   - Every `useShortcut` chord and the `layout.tsx` keydown handler fire exactly
     once (Cmd+K, Cmd+,, Cmd+Shift+C).
   - Esc dismisses any open Dyad surface while the preview holds focus.
   - **Plain keystrokes (letters, arrows, Tab) still reach the previewed app** —
     forwarding must not steal typing.
   - Security: forward only modifier-bearing accelerators, never raw text, or
     this becomes a keylogger from the user's app into Dyad.
2. **Focus enter/exit contract** — focusable DOM placeholder, documented
   enter/exit chord, Esc → `win.webContents.focus()`, DOM-drawn focus ring
   (a native view has no CSS focus ring).
3. **Theme-matched `setBackgroundColor`, gated on first paint**
   - Dark theme: from app selection to first preview paint, no frame renders
     lighter than the panel background.
   - `setVisible(true)` fires on first paint, not `did-finish-load`.
   - Toggling theme while live updates the view background within one frame.
4. **Zoom-aware bounds** (phase-2 correctness, see Finding 5)
   - At 80/100/125/150/200% renderer zoom, the view's rendered rect aligns to
     its DOM placeholder within 1 CSS px on all four edges.
   - Holds after window resize and after a panel drag at each zoom level.

**Not blocking:** a11y landmark + live region on the placeholder
(`role="region"` + `aria-label`, replacing `title="Preview for App N"` at
`:1551`), and reduced-motion handling on the freeze cross-fade. Chromium does
expose a `WebContentsView`'s content to the OS a11y tree, so screen readers
still reach the app — what is lost is one labelled relationship, not a working
experience.

## Technical design

### Architecture

The `preview_iframe` machine **stays renderer-owned**. `state.ts` and
`transition.ts` are already pure and DOM-free; all DOM coupling lives in
`commands.ts` (`PreviewIframeTarget.postMessage`) and `usePreviewIframe.ts`. The
migration is therefore a **second command adapter behind the same interface**,
plus a main-owned view registry. Main owns view lifecycle; the renderer owns
geometry and the machine.

`iframeEpoch` survives but becomes a **reload token**, not a React `key`: the
adapter memoizes `(epoch, src)` and calls `loadURL` only when the pair changes.

**Renderer selection.** Ship `previewRendererDefault: "iframe" | "native"` plus
a pure selector `selectPreviewRenderer({ default, appId })` returning the
effective renderer. Every call site — adapter selection, the visual-editing gate
at `PreviewIframe.tsx:1562` — reads the selector, never the raw setting. Phase
2's selector body is `return default`; the per-app override that powers the
"Switch this app to classic preview" popover is then a one-function change with
no call-site rework.

### The transport bridge (Phase 1)

`worker/dyad-bridge.js`, injected **first** by `injectHTML()`
(`proxy_server.js:188`, ahead of stacktrace/shim), ~60 lines. It exposes
`window.__dyadBridge.post(msg)` / `.onMessage(fn)` and
`window.__dyadTrustedSource(e)`, dispatching to `window.parent.postMessage` in
iframe mode and to IPC (via a preview-only preload's
`contextBridge.exposeInMainWorld("__dyadIpc", …)`) in native mode.

Work in the clients:

- **28 send sites** across five files: `window.parent.postMessage(` →
  `__dyadBridge.post(`. Mechanical find-and-replace.
  (`dyad-shim.js` 32/44/74/132/157/179/192/210/257;
  `dyad-component-selector-client.js` 164/465/508/543/666;
  `dyad-visual-editor-client.js` 110/129/178/202/236/268/290;
  `dyad-screenshot-client.js` 168/181; `dyad_logs.js` 331/345/359/373/387.)
- **4 inbound guards** (`shim:86`, `selector:579`, `visual-editor:308`,
  `screenshot:194`) become `if (!__dyadTrustedSource(e)) return;`.
- **1 transport gate** (`dyad-shim.js:3`) — the `isInsideIframe` early-return
  becomes a bridge-availability check.

So Phase 1 is **one new file plus 33 mechanical edits.**

> **Rejected: mutating the global `window.parent`.** A proxy object assigned to
> `window.parent` in native mode is legal (`[Replaceable]` in WebIDL) and would
> have left all 28 send sites untouched. **It was rejected because it cancels
> part of the migration's own value.** The SDKs most likely to need working
> top-level navigation are exactly the ones that branch on framing: auth SDKs
> commonly do `if (window.parent !== window)` and then refuse or alter a
> redirect flow, preferring a popup or an "open in a new window" affordance.
> Under a global proxy those SDKs would be told they are framed when they are
> not, keep taking the framed branch, and **never attempt the redirect that now
> would have succeeded** — shipping the capability while lying to the callers
> who would use it. `window.top` being `[LegacyUnforgeable]` only partly helps:
> SDKs checking `window.top !== window.self` would stay correct, giving
> inconsistent behavior across SDKs depending on which idiom each happens to
> use, which is worse than either uniform answer. Twenty-eight boring edits beat
> mutating a global that arbitrary user code and AI-chosen third-party SDKs read.
>
> Two narrower scopings were also rejected: wrapping each client in
> `(function(window){…})(proxyOverWindow)` breaks `this`-binding on DOM methods
> ("Illegal invocation") and constructor use; and regex-rewriting client source
> at injection time makes shipped code differ from repo source — the same
> Transparent-Over-Magical failure we would flag in review.

Two further mechanisms tried and rejected during design:

- **A preload cannot host the shim.** With `contextIsolation: true` the preload
  runs in the isolated world and the injected clients in the main world —
  separate `window` objects, so the assignment is invisible to them. The
  preload's only job is `contextBridge.exposeInMainWorld("__dyadIpc", …)`.
- **`event.source` cannot be forged.** `MessageEventInit.source` is a WebIDL
  interface union `(WindowProxy or MessagePort or ServiceWorker)?`; a plain
  object fails conversion with a TypeError. The alternative — a hidden
  same-origin relay iframe whose real `contentWindow` becomes the fake parent —
  would inject a visible iframe into the user's DOM. Patching the four guards
  is cleaner.

### Bounds synchronization (Phase 2)

Bounds must **not** go through contract-driven invoke — 60fps invoke is a
saturation risk per `rules/electron-ipc.md`. Use a dedicated one-way
`ipcRenderer.send`, with rAF-coalesced integer-DIP rects off a `ResizeObserver`,
never React state. Multiply by `webFrame.getZoomFactor()` and re-push on the
`zoomLevel` effect (Finding 5). Must also handle fullscreen, maximize, the
`titleBarStyle: "hidden"` offset, devtools open, and `display-metrics-changed`.

### The `preview_viewport` module

Ships in Phase 1 as a **plain renderer module**, not a state machine — it has a
real job on the iframe today (annotator / loading screen / modal mutual
exclusion is currently ad-hoc). Promote it to `src/preview_viewport/` as a
machine only if native lands, to avoid creating a directory, three test files
and a `boundaries.test.ts` inventory entry that may never be used.

If promoted: it owns only the **discrete** state — `visible`,
`suppressions: readonly Reason[]` (a claim _set_, so competing claims resolve by
"any claim suppresses" rather than last-writer-wins), `insets`, `deviceMode`,
`freeze` — emitting `set-visible` / `set-insets` / `freeze` / `thaw` /
`set-device-mode`. The **continuous** rect stays adapter-owned. Add
`"preview_viewport"` to `MACHINE_DIRECTORIES` (`boundaries.test.ts:7-22`), wire
to `preview_iframe` via a typed facade at a composition root as
`src/app_wiring/preview_error_facade.tsx` already does, and record
`preview_viewport -> none` in the module header.

### Lifecycle and disposal

Views are **destroyed on tab switch**, matching today's iframe behavior, and
history is replayed via the existing `RESTORE_PRESENTATION` path
(`ChatTabs.tsx:624-629`). Tab drag between windows becomes destroy + recreate,
which removes the correlated-receipt handoff that was the riskiest item in the
original phase 3.

**One new cost this introduces:** iframe destroy is synchronous DOM removal;
view destroy is asynchronous renderer-process teardown. Fast tab-flipping races
destroy against recreate for the same `appId`. `rules/state-machines.md` is
explicit — async keyed disposal must stop admission synchronously but keep the
lifetime addressable until its cleanup promise settles, with same-key recreation
blocked behind it. The main registry needs a real keyed disposal barrier, not
`map.delete()`. **Skipped, this ships as an intermittent "preview blank after
switching tabs fast" bug.** Phase 2, not 3.

### Security

Net **better**, not worse.

Today: `sandbox="allow-same-origin allow-scripts …"` grants effectively nothing
for same-origin content; `allow="camera; microphone; geolocation;
display-capture; …"` is ungated; and any preview page can post arbitrary objects
into the renderer's global message listener, where `handleComponentMessage`
(`PreviewIframe.tsx:575+`) consumes `console-log` / `network-*` / `dyad-*` with
essentially no schema validation (`parseComponentSelection` at `:1584` is the
only real validator).

Under a view: `session.fromPartition("persist:dyad-preview-<appId>")` (which
makes the existing `clearSessionData()` menu item at `:1469` a real
`clearStorageData()`), `sandbox: true`, `contextIsolation: true`,
`nodeIntegration: false`, `webviewTag: false`, `setPermissionRequestHandler`,
and a **per-view `setWindowOpenHandler`** that deletes the `isPreviewReferrer`
heuristic in `window_security.ts:118-139` — whose own comment concedes
"Electron does not expose the initiating WebFrameMain to this handler." Keep
`webSecurity: true`; the proxy already makes everything same-origin.

New attack surface is the preview preload — pin its exposed surface with an
allowlist assertion test. Centralizing the four guards into
`__dyadTrustedSource` in Phase 1 also gives one place to add an inbound
payload-shape check, partially closing the validation gap above.

## Implementation plan

### Phase 0 — Spikes (S) · funded

- [ ] **Spike 1: E2E reachability.** Throwaway branch, ~50 lines: hardcode a

> **Corrected during compilation — version skew is smaller than first assessed.**
> A concern was raised that `worker/dyad-sw.js` caches the injected client
> scripts, so a mid-session Dyad update would leave a stale client talking to a
> new renderer. **This does not hold.** `worker/dyad-sw.js` uses no Cache
> Storage at all — it is a fetch-passthrough worker with `skipWaiting()` and
> `clients.claim()` (`:7-21`), with no `caches.open`/`addAll`/`match`. And the
> clients are **inlined** into each HTML response as
> `<script>${content}</script>` (`proxy_server.js:200-260`), not referenced
> by URL, so they cannot be independently cached and arrive fresh with every
> HTML load. The proxy worker also reads them via `readFileSync` at worker
> startup, and a Dyad update restarts the whole process including its workers.
> **The residual risk is genuine but bounded:** an already-loaded preview page
> keeps its old inlined clients until the next navigation or reload. A bridge
> protocol version plus graceful degradation covers it; SW cache invalidation is
> not needed.

## Native preview v1 — what the user gains and loses

v1 is the **phase 2 exit**, behind the "Device preview (beta)" flag.

**Gains:** view rendering via the bridge; real device emulation (touch, DPR,
viewport, media queries); crash isolation with `PREVIEW_CRASHED` recovery;
top-level redirect flows (OAuth, hosted checkout); keyboard/focus contract with
global shortcut forwarding; theme-matched background.

**Losses — state these at the toggle in the UI, not only in this document:**

- **Visual editing is unavailable on the flag.** Turning it on turns off a Pro
  feature. This must appear at the toggle itself.
- The Annotator still uses `html-to-image` — no screenshot improvement yet.
- Tab switches still cold-boot the app; the state-loss problem is unfixed.
- Menus and dialogs briefly freeze the preview.
- Single window and single app only.
- New attack surface (the preview preload) and a second code path with its own
  new bugs.

## Success metrics and guardrails

**Primary** — matched to the reordered #1 problem:

- Device-mode toggle **retention** (users who switch to mobile and keep using it).
- Reduction in mobile-related fix prompts.
- Framing-refusal rate on the flag → ~0.
- Preview-attributed hang rate → materially down.

**Secondary:** crash-free session rate; the back/forward "that didn't work"
signal; time-to-first-successful-preview (guardrail — must not regress).

**Kill signals. Any one pulls the flag:**

- Component-selector activation success −2pp vs the iframe cohort.
- Preview blank/failed-load +1pp vs the iframe cohort.
- Beta opt-out >20%.
- p95 renderer RSS breaching the agreed ceiling.
- **Hang rate failing to improve** — that would mean we paid the full cost and
  got none of the benefit.

## Open questions

If so, Tier 3 freeze has no remaining consumer and the capture pipeline

overlay prototype.

### Positions reversed during the debate

Recorded because they are the substance of the planning, and because anyone
reading the original framing will otherwise re-derive the wrong conclusions.

- **The transport rewrite was over-scoped by roughly an order of magnitude.**
  Initially assessed as ~2000 lines across five files; it is one new file plus
  33 mechanical edits. It is an adapter, not a rewrite.
- **The clever version of that adapter was then rejected by its own author.**
  Mutating the global `window.parent` would have cut the edits to four, but it
  would have cancelled the top-level-navigation win for exactly the SDKs that
  need it (D11).
- **"No more blank previews" was over-claimed.** Nesting depth does not rescue
  embedded third-party widgets. The real win is top-level navigation, which
  reordered the value case and made device emulation the primary justification.
- **Warm-view retention was wrongly stated as the project's motivation.** It is
  not, and dropping it improves the plan.
- **The drag-jank premise did not survive contact with the code** —
  `chat.tsx:150` already disables the transition during resize.
- **A rolling `capturePage()` cache would have traded preview jank for chat
  stutter**, since encoding is synchronous main-process work and main is the
  chat-stream producer.
- **The service-worker version-skew risk was over-stated** and corrected against
  the code during compilation: the SW does no caching and the clients are
  inlined per HTML response, so the real exposure is one stale page-load, not a
  cache-invalidation problem.
